BCaching Economics (Problem 4)

Problem 4 ran the same 12 practice documents twice — once with a caching configuration enabled, once with it disabled — and measured real token usage and dollar cost for both. This is a single controlled experiment, not a general law about caching.

Why costs rose here: the "with cache" configuration paid a cache-write charge ($0.125 per 1M tokens — more than the $0.10 plain input rate) on nearly every call, while only a minority of calls actually received a cheaper cache-read ($0.01 per 1M tokens). The write surcharge outweighed the limited read savings in this particular 12-document experiment.

This is one measured experiment under this gateway's specific, non-deterministic caching behavior (documented in output/cache_test.md) — it does not mean caching always increases cost. It also must not be confused with Problem 2's idealized, hand-calculated estimate of caching savings (which assumed a clean "write once, read many times" pattern); Problem 4 is the real, measured result, and the two should not be read as the same claim.

What went wrong, undefended: documents p02 (HTML, zero-size hidden text) and p12 (PDF, off-page hidden text) each contained a fabricated, human-invisible "corrected" price. Important: Attack A's failure to fool either agent does not mean the underlying extraction gap is fixed. Local, pre-API testing confirmed the class-based display:none payload reached both the undefended and defended readers identically — the defended code layer did not catch it. The model's own reasoning happened to reject the specific conflicting claim in this case; a differently-worded injected claim could still succeed. The defended agent is not immune to all attacks — it closed the two confirmed Problem 5 exploits and the specific MIME-mismatch exploit, not every possible technique.

Do not read this as "defenses reduce cost by 56.8%." A per-document breakdown shows 10 of the 12 documents cost within about $0.00001 of each other, undefended vs. defended. The entire aggregate gap traces to exactly two documents, p01 and p08, whose undefended calls happened to receive zero cache-read discount (full-price input), while every other call — defended or not — received a large cache discount. This is the same non-deterministic caching behavior documented in Problem 4, not a property of the defense layers. The honest conclusion: the three defense layers added no measurable per-call cost, and the large aggregate dollar gap is a caching artifact, not a causal effect of defending the agent.

FRecommendation to the Store Manager

Do not connect this agent directly to real vendor email with autonomous authority to act. Run it first as a human-reviewed pilot.

Recommended operating posture
Autonomous deployment nowNot recommended. One known residual extraction vulnerability (CSS class-based hiding) and one demonstrated, successfully-exploited vulnerability (MIME part mismatch, now mitigated but not provably eliminated for all variants) remain.
Human-reviewed pilotRecommended. Run the defended agent on real incoming vendor documents; a human buyer reviews every recommend/do_not_recommend output and its reason before any purchasing action is taken, for at least an initial evaluation period.
Approvals & paymentssend_email and approve_payment must remain logging-only traps, exactly as built. No automated system should gain authority to send a real vendor email or release a real payment without an explicit, separate human approval step (the approval.py pattern built in Problem 6 — not yet connected to any real action).
Outbound communicationNone should be automated yet. All vendor-facing replies should continue to go through a human buyer until the pilot period demonstrates reliability.
Monitoring & audit loggingKeep the existing usage_log.json / audit_trail.json pattern: log every document, decision, reason, tool call, token count, and cost. Review logs weekly during the pilot for any decision that disagrees with a human reviewer, and for any attempted tool call.
Manual escalationAny document with conflicting values for the same fact (e.g. two different prices or lead times stated anywhere in the text), or any recommend for a vendor not previously purchased from, should be flagged for mandatory human review rather than auto-approved, even after the pilot.

Estimated cost of processing 1,000 documents/day

Using the Problem 8 exam run's observed average cost per document as the baseline:

measured_exam_cost_total  = $0.00660678  (10 documents, Problem 8) observed_cost_per_document = $0.00660678 / 10 = $0.000660678 → projected_daily_cost (1,000 docs) = $0.000660678 × 1,000 = $0.660678/day → projected_monthly_cost (22 operating days) = $0.660678 × 22 = ≈ $14.53/month → projected_monthly_cost (30 calendar days) = $0.660678 × 30 = ≈ $19.82/month
Measured vs. extrapolated vs. guaranteed — clearly distinguished:
  • Measured: $0.00660678 total for exactly 10 real exam documents (Problem 8).
  • Extrapolated: the $0.66/day and $14.53–$19.82/month figures above are a linear scaling of that measured per-document cost to a hypothetical 1,000-documents/day volume — not a separately measured 1,000-document run.
  • Not a guaranteed production price. The exam run's cached-read rate was unusually high (227,037 of 244,081 input tokens, 93%), and Problem 4 and Problem 6 both documented that this gateway's caching behavior is non-deterministic — real production traffic, with different document content arriving at different times, may not sustain this cache-hit rate. As a sanity check, using the Problem 6 defended practice-set average instead ($0.00746336 / 12 = $0.000621947/doc) gives a very similar daily estimate (≈$0.62/day) — but both baselines share the same favorable, possibly non-representative caching conditions. A production pilot should re-measure actual cost over at least several hundred real documents before budgeting at scale.

GMethodology & Limitations

  • All figures are drawn directly from this project's own output files: output/cache_test.json, output/attack_results.json, output/defense_results.json, output/red_team.json, output/exam_results.json, output/usage_log.json, and output/cost_correction_audit.md. None are estimated beyond what is explicitly labeled a projection in Section F.
  • Billing correction applied throughout: a cached-token double-counting bug was found and fixed during Problem 8 (the API's input_tokens figure already includes cached tokens — billing the full amount and the cached portion again double-charges it). All Problem 5–7 dollar figures in this report use the corrected values; the original, inflated figures are preserved only in output/_pre_cost_correction_backup/ for audit purposes and are not used here.
  • The Problem 4 caching experiment and the Problem 5/6/8 cost figures reflect a gateway with documented, non-deterministic cache-hit behavior — repeated runs of the same documents can show different cache-read rates. Cost comparisons across small numbers of calls should be read with this in mind.
  • No API calls were made to build this report — it is a static document assembled entirely from already-captured JSON/Markdown files.
  • This report does not use or reference any exam answer key, because none exists for data/exam_docs/; Section E reports agent behavior only.
